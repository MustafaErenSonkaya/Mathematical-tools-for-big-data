# Streaming Outlier Detection with Smart Alerts

This project watches three (simulated) sensors, a **temperature** sensor, a
**CPU usage** sensor and a **pressure** sensor, notices when one of them starts
behaving strangely, and sends **one** clear alert per problem instead of
hundreds of noisy ones. Everything shows up live on a dashboard in your browser.

You don't need to know Docker, Prometheus or Grafana to run it. Follow the
steps below and you'll have it running in about 10 minutes.

> [CHAT.md](CHAT.md) documents how the project was built: the full conversation with
> the AI assistant (Claude Code) that wrote it, including plain-English
> explanations of the ideas behind it.

## 1. What does it do?

Imagine a machine with a thermometer that reports a value every second.
Usually it says about 22 °C, wobbling a little. Sometimes something goes
wrong and the value jumps to 24 °C for half a minute. We want to **notice**
that, and **tell someone**, but in a smart way.

The project has two halves:

**The detector** looks at each new value and asks: *"compared to the last 100
normal values, how unusual is this one?"* The answer is a number called the
**z-score**. Around 0 means normal. Above 3 (or below −3) means very unusual.

**The alert manager** decides when a human should actually be told. That
matters more than it sounds. In one simulated hour:

| Approach | Alerts you would receive |
|---|---|
| Alert on every unusual value | **697** |
| This project's smart alerts | **24** |

Both versions catch the same problems. The first one just tells you about
each problem 30 times in a row, so after a day you'd ignore all of them.
The smart version follows four rules:

| Rule | What it prevents |
|---|---|
| Only alert after **3 unusual values in a row** | A single random blip waking someone up |
| Send **one ALERT** at the start and **one RESOLVED** at the end, nothing in between | 30 messages about the same problem |
| Start alerting above 3, but only call it fixed after **5 values in a row below 2** | Flip-flopping ALERT / RESOLVED / ALERT when the value hovers around 3 |
| After a problem is fixed, wait **60 seconds** before alerting again (repeats are only counted as "suppressed") | Being paged again for the same problem coming back a moment later |

The sensors are fake (generated by the program), and the program adds
problems on purpose at random moments, so there's always something to see.

## 2. Words you'll meet

| Word | What it means here |
|---|---|
| **Docker** | A tool that runs programs in sealed boxes called **containers**. Each container already has everything it needs, so you don't install Python, Prometheus or Grafana yourself. Docker downloads and runs them for you. |
| **Docker Desktop** | The app you install on Windows or Mac to get Docker. It must be **open** while the project runs. |
| **Docker Compose** | Part of Docker. It reads `docker-compose.yml` and starts several containers together with one command. |
| **Prometheus** | A database for numbers over time. Every 5 seconds it asks our app "what are your current values?" and stores the answers. |
| **Grafana** | The dashboard website. It reads from Prometheus and draws the charts. |
| **Outlier** | A value that is very different from the recent normal values. |
| **z-score** | How many "normal wobbles" (standard deviations) a value is away from the average. 0 = perfectly average, ±3 = very unusual. |
| **Alert** | A message saying "this sensor has a problem". **RESOLVED** means "it's fine again". |
| **localhost** | "This computer". `http://localhost:3000` is a website running on your own machine. |

When it runs, three containers work together:

```
  [ app ]  --------->  [ Prometheus ]  --------->  [ Grafana ]  --------->  you (browser)
  makes sensor         collects the numbers         draws the charts        http://localhost:3000
  data, detects        every 5 seconds and
  outliers, alerts     keeps their history
```

## 3. How to run it (step by step)

### Step 1: Install Docker Desktop (one time only)

Download it from **https://www.docker.com/products/docker-desktop/**. It's free
for personal and educational use.

<details>
<summary><b>Windows</b></summary>

1. Download **Docker Desktop for Windows** and run the installer.
2. Keep the default options. If it asks about **WSL 2**, leave it selected.
   WSL is a Windows feature Docker needs.
3. Restart your computer if the installer asks.
4. Open **Docker Desktop** from the Start menu. The first time, accept the
   terms. You can skip creating an account.
5. Wait until the bottom-left corner of Docker Desktop says **Engine running**
   (green).

If Docker says WSL needs updating, open **PowerShell** and run `wsl --update`,
then start Docker Desktop again.
</details>

<details>
<summary><b>macOS</b></summary>

1. Download **Docker Desktop for Mac**. Pick **Apple Silicon** for M1/M2/M3/M4
   Macs, or **Intel** for older Macs. Not sure? Apple menu → *About This Mac*
   → look at "Chip".
2. Open the `.dmg` file and drag **Docker** into **Applications**.
3. Open Docker from Applications, accept the terms and allow what it asks for.
   You can skip creating an account.
4. Wait until Docker Desktop shows **Engine running**.
</details>

<details>
<summary><b>Linux</b></summary>

Install **Docker Engine** and the **Compose plugin** for your distribution by
following https://docs.docker.com/engine/install/. To run `docker` without
`sudo`, also follow the "post-installation steps" page.
</details>

**Check it worked:** open a terminal (Windows: **PowerShell**; Mac: **Terminal**)
and type:

```bash
docker --version
```

If it prints something like `Docker version 28.x`, you're ready.

### Step 2: Download this project

**Option A, no git needed (easiest):**
1. On this project's GitHub page, click the green **Code** button →
   **Download ZIP**.
2. Unzip it somewhere easy to find, for example your Desktop.
   On Windows: right-click the ZIP → **Extract All**.

**Option B, with git:**

```bash
git clone https://github.com/MustafaErenSonkaya/Mathematical-tools-for-big-data.git
```

### Step 3: Start it

Make sure **Docker Desktop is open** and says **Engine running**. Then:

- **Windows:** open the project folder and **double-click `start.bat`**.
  (If Windows shows "Windows protected your PC", click **More info → Run anyway**.
  It's a plain text script, so you can open it in Notepad to see exactly what it does.)
- **macOS / Linux:** open a terminal in the project folder and run:

  ```bash
  bash start.sh
  ```

The **first start takes a few minutes**. Docker downloads about 1 GB
(Python, Prometheus and Grafana) and builds the app. Later starts take
seconds. When it's done, your browser opens **http://localhost:3000**
automatically.

<details>
<summary>Prefer typing the command yourself?</summary>

Open a terminal **inside the project folder** (the one that contains
`docker-compose.yml`) and run:

```bash
docker compose up -d --build
```

`up` starts the containers, `-d` runs them in the background, and `--build`
builds the app first. Then open http://localhost:3000.
</details>

### Step 4: Watch the dashboard

Open **http://localhost:3000**. You don't need to log in.

- The charts start **empty** and fill up during the first minute. The detector
  also needs 30 values to learn what "normal" looks like before it judges anything.
- Problems are injected at random. **Expect the first alert within about
  1 to 5 minutes.** You'll see a red block appear in the "Alert state" timeline.
- The page refreshes itself every 5 seconds.

[Section 4](#4-reading-the-dashboard) explains every chart.

### Step 5: Stop it

- **Windows:** double-click **`stop.bat`**
- **macOS / Linux:** `bash stop.sh`
- **Or type:** `docker compose down` (in the project folder)

Your data (chart history, alerts) is **kept** for next time. Closing the
browser does **not** stop the project. Use the stop script. Quitting Docker
Desktop also stops everything.

<details>
<summary>Remove everything (free up disk space)</summary>

Run this in the project folder:

```bash
docker compose down -v --rmi all
```

`-v` deletes the stored data, and `--rmi all` deletes the downloaded images.
Then you can delete the project folder.
</details>

## 4. Reading the dashboard

At the top, the **Sensor** dropdown chooses which sensors to show (default: all).
The time picker on the right chooses how far back to look.

**Alert state - all sensors.** One bar per sensor. **Green = NORMAL**,
**red = ALERTING**. This is the quickest "is anything wrong?" view.

Then there's one section per sensor:

| Panel | What you see | How to read it |
|---|---|---|
| **Value** | The raw sensor reading (blue line). **Red dots** are values the detector flagged as outliers. | Normal data wobbles around a level that slowly drifts up and down. That drift is normal and is *not* flagged. Problems look like sudden jumps or steady ramps. |
| **z-score** | How unusual each value is (purple line), with dashed lines at **±2** (orange) and **±3** (red). | Inside ±2: normal. Beyond ±3: outlier. Three outliers in a row start an alert. The alert ends after 5 values in a row back inside ±2. |
| **Alert state** | Green/red timeline for this sensor. | Each red block is **one** incident, which sent exactly one ALERT and one RESOLVED message. |
| **Alerts fired** | Number of ALERTs in the selected time range. | |
| **Alerts suppressed** | Number of times a problem came back during the 60 s cool-down and was **counted but not sent**. | If the problem is still going when the cool-down ends, a normal alert is sent then. Nothing is lost. |

**Why don't I see a red dot for every problem?** The app makes a value every
second, but Prometheus only takes a sample every 5 seconds, so a one-second
spike can fall between samples. The alert timeline and the counters are
always complete.

## 6. Troubleshooting

| Problem | Fix |
|---|---|
| `start.bat` says **"Docker is not running"**, or you see `error during connect` / `cannot connect to the Docker daemon` | Open Docker Desktop and wait until it says **Engine running**, then try again. |
| **`port is already allocated`** | Something else on your computer is using port 3000, 8000 or 9090 (often another Docker project). Stop it in Docker Desktop (**Containers** → ■ stop), or change the left-hand number in `docker-compose.yml`, e.g. `"127.0.0.1:3001:3000"`, and open http://localhost:3001 instead. |
| **`no configuration file provided: not found`** | You ran the command in the wrong folder. `cd` into the folder that contains `docker-compose.yml`. |
| Browser shows **"This site can't be reached"** | Wait 20 seconds and refresh. Grafana takes a moment to start. Check that all three containers are running: `docker compose ps`. |
| The charts are **empty** | Wait a minute, and make sure the time range (top right) is something like "Last 15 minutes". |
| **No alerts yet** | Problems are random. Give it a few minutes. |
| Docker Desktop on Windows complains about **WSL** or **virtualization** | Run `wsl --update` in PowerShell and restart. If it mentions virtualization, it has to be switched on in your computer's BIOS/UEFI settings (search "enable virtualization" + your laptop brand). |
| macOS/Linux: **`permission denied`** when running `./start.sh` | Run it as `bash start.sh` instead. |
| I changed `config.yaml` but nothing changed | Restart with a rebuild: `docker compose up -d --build`. |
| Grafana won't accept my password from `.env` | Grafana only reads it the first time. Reset with `docker compose down -v` (this deletes stored data), then start again. |

## 7. Changing the settings

All the numbers live in [`config.yaml`](config.yaml), with a comment on each
line. The most interesting ones:

| Setting | Default | Effect |
|---|---|---|
| `stream.anomaly_probability` | `0.004` | How often problems are injected. Higher = more alerts. |
| `stream.seed` | `42` | Same seed = same "random" data every start. Set to `null` for different data each time. |
| `detector.window_size` | `100` | How many recent normal values define "normal". |
| `detector.method` | `zscore` | `robust` uses median/MAD instead of mean/std, which is less disturbed by extreme values. |
| `alerts.k_consecutive` | `3` | Unusual values in a row needed to start an alert. |
| `alerts.m_consecutive` | `5` | Calm values in a row needed to end it. |
| `alerts.cooldown_seconds` | `60` | Quiet period after an alert is resolved. |

After changing it, restart with `docker compose up -d --build`.

## 9. How it works

### The pieces

```
 stream.py           detector.py              alerts.py               notifier.py
+-----------+  value +---------------+  z    +----------------+ event +-------------------+
| simulated | -----> | OnlineDetector| ----> |  AlertManager  | ----> | console (colors)  |
| sensors   |        | (per sensor)  |       | state machine  |       | alerts.jsonl      |
+-----------+        +---------------+       +----------------+       | (email, Telegram) |
                                                   |                   +-------------------+
                                                   v
                                             metrics.py --> :8000/metrics --> Prometheus --> Grafana
```

```
outlier-detector/
├── src/
│   ├── stream.py       fake sensors + injected problems
│   ├── detector.py     z-score over a rolling window
│   ├── alerts.py       NORMAL/ALERTING state machine (the "smart" part)
│   ├── notifier.py     console + alerts.jsonl (easy to add email/Telegram)
│   ├── metrics.py      numbers for Prometheus
│   └── main.py         connects everything
├── tests/              automatic tests (pytest)
├── config.yaml         every setting
├── Dockerfile          how the app container is built
├── docker-compose.yml  starts app + Prometheus + Grafana together
├── prometheus/         Prometheus settings (what to collect, how often)
├── grafana/            datasource + dashboard, loaded automatically
├── start.bat / stop.bat    Windows double-click scripts
└── start.sh  / stop.sh     macOS/Linux scripts
```

### `src/stream.py`: the data source
A **generator** that yields `Reading(sensor, timestamp, value, anomaly)` objects.
Each value is `baseline + slow sine drift + Gaussian noise`, and sometimes an
anomaly is added:

| anomaly | what it looks like | why it is interesting |
|---|---|---|
| spike | 1 point, 6 to 10 sigma away | should **not** page anyone (K=3 filters it) |
| shift | level jumps 5 to 8 sigma for 10 to 30 points | the classic "something broke" |
| drift | level ramps up to 8 to 12 sigma over 30 to 60 points | slow problems that a fixed threshold catches late |

**Simulated clock.** The timestamps are `start + tick * interval`. Normal
mode sleeps between ticks, and fast mode skips the sleep. Everything
downstream uses the timestamps, never `time.time()`. So fast mode (and the
tests) behave exactly like real time, including the 60 s cooldown.

The `anomaly` label is the ground truth, for debugging only. The detector
never sees it.

### `src/detector.py`: "is this point weird?"
One `OnlineDetector` per sensor keeps a rolling window (default 100) of
recent normal values and computes:

```
z = (x - center) / spread
```

- **zscore** mode: mean and standard deviation.
- **robust** mode: median and `1.4826 * MAD`. A few extreme values barely move
  these numbers, which makes this mode safer when junk leaks into the window.

Three rules make it trustworthy:
1. **Score before adding.** Otherwise the point would be compared against
   statistics it already influenced, which makes it look less extreme.
2. **Warmup** (default 30 points). Statistics from 3 points are meaningless,
   so the detector returns `z=None` until it has enough data.
3. **Outliers stay out of the window.** If the 20 points of a shift were added,
   the window would learn the anomaly as the new normal and the alert would
   end too early. The trade-off: a *permanent* level change keeps alerting
   until a human looks at it. For alerting, that is usually the right choice.

The slow sine drift is *not* flagged, because normal points keep entering the
window and the mean follows the drift.

### `src/alerts.py`: "should a human hear about it?"
A per-sensor state machine with two states:

```
           K consecutive |z| > 3.0                 (fires ALERT)
  NORMAL -------------------------> ALERTING
     ^                                  |
     +----------------------------------+
           M consecutive |z| < 2.0                 (fires RESOLVED)
```

| rule | default | problem it solves |
|---|---|---|
| K consecutive outliers to enter | 3 | single spikes and random noise |
| exit only below 2.0, not 3.0 (**hysteresis**) | 2.0 | flapping when z hovers around 3 |
| M consecutive calm points to exit | 5 | one lucky calm point ending an incident early |
| cooldown after RESOLVED | 60 s | the same problem paging again a minute later |

- Exactly one `ALERT` when entering and one `RESOLVED` when leaving, nothing
  in between.
- `RESOLVED` includes `duration_seconds` (measured from the first outlier of
  the streak) and `peak_z` (the most extreme z, keeping its sign).
- Each incident gets a unique id like `cpu-3f9a1c2b` (from `uuid4`).
- During cooldown, a would-be alert is **counted** in `suppressed_count`
  (once per streak, not once per point) instead of being fired. If the streak
  is still going when the cooldown ends, an alert opens. At that point the
  problem is clearly persistent.

### `src/notifier.py`: delivery
All notifiers share one method, `send(event)`:
- `ConsoleNotifier`: red ALERT and green RESOLVED lines.
- `JsonlNotifier`: appends one JSON object per line to `alerts.jsonl`. It is
  easy to grep and to load with pandas, and appending never corrupts old lines.
- `NotifierGroup`: fans out to several notifiers. If one fails (say, the email
  server is down), the others still get the event.

**Adding a channel:** subclass `Notifier`, implement `send`, and add it in
`build_notifiers()` in `main.py`. The module docstring has a Telegram example.

### `src/metrics.py` and the monitoring stack

```
 app container                  prometheus container             grafana container
+---------------------+  pull  +----------------------+  query  +---------------------+
| stream -> detector  | <----- | every 5 s: GET       | <------ | dashboard panels    |
| -> alerts -> Metrics|        | app:8000/metrics,    |  PromQL | run PromQL every 5 s|
| serves /metrics     |        | stores samples (TSDB)|         | and draw charts     |
+---------------------+        +----------------------+         +---------------------+
```

1. **App**: after each reading, `src/metrics.py` updates in-memory gauges and
   counters. `prometheus_client` serves their *current* values as text on
   port 8000. The app doesn't store history and doesn't push anything.
2. **Prometheus** *pulls* (scrapes) that page every 5 seconds
   (`prometheus/prometheus.yml`) and saves each number with a timestamp in
   its time-series database. That's where the history lives.
3. **Grafana** stores no metrics. Each panel sends a PromQL query to Prometheus
   (e.g. `sensor_zscore{sensor="cpu"}`) and draws the result. The datasource
   and dashboard come from `grafana/provisioning/`, so nothing is clicked
   together by hand.

| Metric | Type | Meaning |
|---|---|---|
| `sensor_value{sensor}` | gauge | latest raw reading |
| `sensor_zscore{sensor}` | gauge | latest z-score (NaN during warmup, shown as a gap) |
| `sensor_is_outlier{sensor}` | gauge | 1 if the latest reading is an outlier |
| `sensor_alert_state{sensor}` | gauge | 0 = NORMAL, 1 = ALERTING |
| `alerts_fired_total{sensor}` | counter | ALERT events |
| `alerts_suppressed_total{sensor}` | counter | alerts swallowed by the cooldown |
| `points_processed_total{sensor}` | counter | readings processed |

A *gauge* can go up and down (current value). A *counter* only goes up, and
Prometheus' `increase()` turns it into "how many in this time range". All
counters start at 0 on startup; otherwise a counter would only appear on its
first increment, and `increase()` would miss that first event.

### Docker files
- `Dockerfile`: `python:3.11-slim`. Dependencies are installed in their own
  cached layer, and the app runs as the non-root `appuser`, which can write
  only to `/app/data`.
- `docker-compose.yml`: the three services, named volumes (data survives
  restarts), Grafana with anonymous read-only access, and ports bound to
  `127.0.0.1` so only your own computer can reach them.
- `prometheus/prometheus.yml`: the scrape job.
- `grafana/provisioning/`: the datasource, dashboard provider and dashboard JSON.

### `tests/`
- `test_alerts.py`
  - a **20-point sustained anomaly** produces exactly 1 ALERT and 1 RESOLVED
    with the same incident id;
  - a **single spike** produces no alert when K=3;
  - **cooldown** suppresses a repeat (and counts it once);
  - plus unit tests for hysteresis/flapping, consecutive-ness, signed peak,
    new ids after cooldown, and independence between sensors.
- `test_detector.py`: warmup, score-before-add, no window pollution, robust
  vs classic under contamination, constant signals.
- `test_stream_and_main.py`: fast mode, determinism with a seed, all anomaly
  types appear, JSONL output, a full end-to-end run from `config.yaml` whose
  metrics must match the events that happened.
- `test_metrics.py`: all 7 metrics are exposed, and they track outliers,
  alert state, fired and suppressed alerts correctly.

### Ideas to explore next
- Plot `alerts.jsonl` against the stream's ground-truth labels to measure
  precision and recall, then tune K, M and the thresholds.
- Add an "accept new normal" rule: after N minutes of a stable shift, let the
  window re-learn.
- Replace `np.mean`/`np.std` over the window with running sums (add the new
  value, subtract the one leaving the window) for O(1) updates.
- Add a real notifier (email or Telegram) using the pattern in `notifier.py`.
